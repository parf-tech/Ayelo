# Phase 0 : audit d'accessibilité WCAG 2.2 AA de l'application mobile Ayelo

> Note du 2026-11-16 : `ProgressBar.tsx`, cité plus bas, a été supprimé (remplacé par `Stepper`) ; les renvois à ses lignes décrivent l'état du code au 2026-11-08.

Livrable de la phase 0 (volet accessibilité) du prompt maître `docs/design/PROMPT-UIUX-EXPERT.md`, sections 4 (principes 5 et 8) et 8 (critères de qualité).

## 0. Périmètre, méthode et limites

**Limite majeure : rien n'a été rendu.** Aucun émulateur, simulateur ni appareil n'était disponible pour cet audit. Tout ce qui suit vient de la lecture du code (`mobile/src`, `mobile/app`, `mobile/app.json`) et des jetons (`mobile/src/theme/tokens.ts`). Un critère noté « Réussi » signifie « le code est conforme » ; il ne signifie pas « vérifié sur appareil ». Les tests Jest ne voient pas le rendu (prompt maître, phase 0). Les points qui ne se confirment que sur un vrai appareil sont marqués **Inconnu** et renvoyés au plan de test de la section 5.

Méthode des contrastes : calcul manuel avec la formule WCAG 2.2. Pour chaque canal sRGB `c = v/255`, `lin = c/12.92` si `c <= 0,04045`, sinon `lin = ((c + 0,055)/1,055)^2,4`. Luminance relative `L = 0,2126 R + 0,7152 G + 0,0722 B`. Rapport `(L1 + 0,05)/(L2 + 0,05)` avec `L1 >= L2`. Précision : 4 décimales sur L, rapports arrondis au centième (erreur estimée inférieure à 0,02). Les résultats qui tombent à moins de 0,1 d'un seuil sont signalés « marge faible » et doivent être confirmés par un script (voir P1-9).

Étiquettes (prompt maître, section 7) : *fait (source)* = lu dans le code ; *hypothèse* = à valider ; *inconnu* = demande un appareil.

Plateformes : application native iOS et Android (Expo). La cible web (`app.json`, `asyncRoutes.web`) n'est pas auditée.

Note b : le jeton `overlay` n'est référencé nulle part dans `mobile/src` (recherche sur `colors.overlay`, aucun résultat). Sur une photo blanche (pire cas), un voile noir `#000000` doit donc avoir une opacité d'au moins **0,55** (255 x (1 - a) <= 119), et un voile `#1B1A19` d'au moins **0,60**. Prévoir un dégradé qui atteint cette opacité sous le texte, ou une bande pleine.

### 3.1 Rôles, étiquettes, indices, états, valeurs

### 3.2 Régions vivantes et annonces

- Recherche : `accessibilityLiveRegion` apparaît 10 fois (liste de la section 2.3, ligne 4.1.3). `announceForAccessibility`, `AccessibilityInfo.announce` et `setAccessibilityFocus` : **aucune occurrence**.
- Conséquence sous iOS : bannières d'erreur, toasts, erreurs de champ, statut d'appel, « écrit… », compteur de photos, valeur du stepper sont tous **silencieux**. Sous Android (TalkBack), les régions vivantes fonctionnent, mais la région vivante n'est pas déclenchée au montage d'un nœud déjà plein : à confirmer.
- Match : aucun message. `MatchScreen` pousse un nouvel écran (route `/match`) ; le focus lit en principe le premier élément après la transition (l'avatar est masqué, donc le titre `C'est un match !`, `MatchScreen.tsx:41`). **Inconnu**.
- Erreurs de swipe (`DiscoverScreen.tsx:98`) et résultat « J'aime » : pas d'annonce. Après une action par bouton, la carte courante disparaît et le focus est perdu (il n'est pas replacé sur la carte suivante).

### 3.3 `importantForAccessibility` et groupes

- `Banner.tsx:73` et `CheckboxField.tsx:56`, `ChoiceCard.tsx:54` : `no-hide-descendants` sur des éléments décoratifs. Correct.
- `SwipeCard` de dessous (`interactive={false}`) : `accessible={false}` seulement ; ses enfants restent exposés. Manque `importantForAccessibility="no-hide-descendants"` et `accessibilityElementsHidden`.
- `EmptyState` : voir 4.1.2 (groupe qui avale le bouton).
- `ListRow` : bonne gestion du cas « avec contrôle à droite » (`ListRow.tsx:68-72`).

### 3.4 Ordre du focus et piégeage dans les fenêtres modales

- Aucun composant `Modal`. Les « feuilles » (menu de conversation, menu du détail, confirmation de blocage) sont des vues insérées en ligne.
- `accessibilityViewIsModal` n'est utilisé qu'une fois (`ProfileDetailScreen.tsx:155`), sur une vue non flottante : propriété iOS uniquement, sans équivalent Android, sans déplacement du focus à l'ouverture, sans geste d'échappement (`onAccessibilityEscape`), sans retour du focus sur le bouton déclencheur.
- Le menu de conversation (`ConversationScreen.tsx:247`) n'a aucun traitement.
- Pas de piège de clavier ; mais pas de piégeage utile non plus : le lecteur d'écran continue de parcourir l'arrière-plan.

### 3.6 Taille de police

- `allowFontScaling` : aucune occurrence, donc activé partout (bon pour 1.4.4). `maxFontSizeMultiplier` : aucune occurrence. Aucune limite : les composants à hauteur fixe (section 2.1, risques de 1.4.4) cassent avant tout autre.
- `MainTabs.tsx:30` fixe `fontSize: 12` pour les libellés d'onglets ; `TextField.tsx:90` et `ConversationScreen.tsx:208` fixent `fontSize: 16` (ne suit pas les jetons, mais suit l'échelle système).
- Recommandation : pas de plafond sur le texte courant (c'est la règle WCAG) ; plafond de 1,6 à 2,0 seulement sur les libellés d'onglets et les pastilles où le conteneur est contraint par la plateforme (P2).

### 3.7 `hitSlop`

Un seul usage (`Button.tsx:48`, 4 pt). Les cibles sont déjà de 44 pt et plus ; `hitSlop` n'est pas nécessaire. Le risque est inverse : des zones qui se recouvrent entre boutons voisins sans espacement (`PhotosManager.tsx:186-210`). Ajouter un `gap` d'au moins 8 pt entre cibles voisines.

### 3.8 Clavier : évitement, touche d'action, focus

- `KeyboardAvoidingView` avec `behavior="padding"` sous iOS, aucun comportement sous Android (`ScreenContainer.tsx:29`) ; pas de `keyboardVerticalOffset` (nécessaire si un en-tête natif ou une barre d'onglets est présent). Le pied de page est dans le `KeyboardAvoidingView`, donc le bouton principal remonte avec le clavier : bon. `keyboardShouldPersistTaps="handled"` : bon (`ScreenContainer.tsx:34`).
- `returnKeyType`, `onSubmitEditing`, `blurOnSubmit`, `autoFocus` : aucune occurrence. À l'écran de connexion, la touche « retour » ne passe pas au mot de passe et ne soumet pas.
- `TextField` n'expose pas de `ref` : l'enchaînement par code (`focus()` sur le champ suivant) est impossible sans ajouter une propriété `inputRef`.
- Aucun `setAccessibilityFocus` à l'ouverture d'un écran ou d'une erreur.

### 3.9 Sélecteur de date (`DateSelector`) : coût pour le lecteur d'écran

Écran critique (contrôle d'âge, `BirthdateScreen`). Mesure par lecture :
- Trois colonnes d'éléments `radio` : 31 jours + 12 mois + `birthYears()` années (de l'ordre de 80 à 100 valeurs). Soit environ **125 à 145 arrêts de balayage** pour parcourir le contrôle ; chaque arrêt lit « Jour 17, bouton radio, sélectionné ou non » (`DateSelector.tsx:129-133`).
- Pour atteindre le bouton « Continuer » depuis le titre, un utilisateur de VoiceOver doit balayer ces 125 arrêts ou utiliser la navigation par éléments (rotor) ; il n'existe aucun saut rapide.
- Trois `ScrollView` imbriquées de 176 pt dans le défilement de l'écran : piège de défilement pour les doigts et pour le lecteur d'écran (`DateSelector.tsx:114-125`, `ScreenContainer scroll`).
- Les hauteurs fixes se coupent à 200 % (`DateSelector.tsx:20-21`).
- Une année faite à la main (par exemple 1987) exige de faire défiler jusqu'à la bonne ligne (`initialScrollYear` = année - 25 amène à 25 ans, `BirthdateScreen.tsx:123`).
- Verdict : réussit techniquement 4.1.2 et 2.5.7, mais **inutilisable en pratique** pour VoiceOver et TalkBack, et lourd pour l'accès par commutateur.

Alternatives (décision du propriétaire sur la dépendance, recommandation sans dépendance en premier) :
1. **Trois champs numériques** jour (2 chiffres), mois (2 chiffres ou liste courte), année (4 chiffres) : modèle « date input » du GOV.UK Design System. Aucune dépendance, clavier numérique natif, étiquettes visibles, `autoComplete` `birthdate-day`, `birthdate-month`, `birthdate-year` (Android), validation existante `toIsoBirthdate` réutilisable. Coût lecteur d'écran : 3 arrêts.
2. Sélecteur natif `@react-native-community/datetimepicker` (dépendance à valider ; roue réglable de VoiceOver sous iOS, boîte de dialogue système sous Android).
3. Conserver le composant mais exposer chaque colonne comme **un seul** élément `adjustable` (`accessibilityRole="adjustable"`, `accessibilityValue`, actions `increment` et `decrement`) : 3 arrêts, mais comportement moins courant.

Recommandation : option 1.

## 6. Décisions pour le propriétaire (avec recommandation)

3. **Orientation** : autoriser le paysage (recommandé pour l'accessibilité) ou garder le portrait avec exception documentée.
4. **Toasts** : durée illimitée quand une action existe ou quand le lecteur d'écran est actif (recommandé).
5. **Vraie feuille modale (`Modal`)** pour les menus de conversation et de détail, ou menus en ligne améliorés (P1-8). Recommandation : `Modal` natif, car il piège le focus sur les deux plateformes.

## 7. Hypothèses à valider

- *Hypothèse à valider* : sous iOS, un conteneur `accessible` empêche de focaliser séparément ses enfants interactifs (comportement attendu de React Native) ; confirmer avec VoiceOver sur `EmptyState`.
- *Hypothèse à valider* : sous Android, `accessibilityLiveRegion="polite"` annonce un `Banner` monté avec son texte (certaines versions n'annoncent qu'un changement de texte d'un nœud déjà monté).
- *Hypothèse à valider* : les `lineHeight` des jetons grandissent avec la police sur les deux plateformes.
- *Inconnu* : ordre de balayage de la liste inversée de la conversation ; annonce du titre d'écran sans en-tête natif ; rendu des libellés d'onglets à 200 % ; comportement du focus clavier externe sous Android.
- *Inconnu* : hauteur et chevauchement des éléments à 320 pt ; la largeur de 380 pt de l'en-tête de conversation est une estimation par addition (libellé « Retour » + trois boutons de glyphe + avatar + marges), pas une mesure.
- *Fait (code)* : aucune occurrence de `announceForAccessibility`, `returnKeyType`, `maxFontSizeMultiplier`, `reduceMotionChanged`, `setAccessibilityFocus`, ni de composant `Modal` dans `mobile/src` et `mobile/app`.
